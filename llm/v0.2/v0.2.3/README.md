# link_llm — 나만의 작은 언어 모델 (v0.2.3)

**일반화 · 튜닝.** 모델 구조·문맥은 v0.2.2 그대로이고, **학습을 다듬는 도구 3개**를 더합니다.

## 한 걸음 — 도구 3개

| # | 도구 | 코드 | 무엇을 하나 |
|---|---|---|---|
| ① | **dropout** | `nn.Dropout(p)` (tanh 뒤) | 학습 중 은닉 뉴런 일부를 꺼 특정 경로 의존을 막음 |
| ② | **weight tying** | `fc2.weight = emb.weight` | 출력층과 임베딩이 **한 텐서를 공유** → 파라미터 V×H 절약 |
| ③ | **LR 스케줄** | `torch.optim.lr_scheduler` | 학습이 진행될수록 학습률을 줄여 곱게 수렴 |

## 구조

```
(앞 N토큰) → 임베딩 concat(N·E) → fc1 → [BatchNorm(선택)] → tanh → [Dropout] → fc2 → logits(V)
                                                                                ↑ (선택) emb.weight 공유
```

- `DROPOUT=0.0` 이면 Dropout 이 항등이라 **v0.2.2 와 완전히 같아져요**.
- **weight tying 은 `HIDDEN == EMBED` 가 필수**입니다 (`fc2.weight`(V,H) 와 `emb.weight`(V,E) 모양이 같아야 함).
  어긋나면 `lm.py` 가 이유를 설명하며 멈춰요.

| `LR_SCHEDULE` | 동작 |
|---|---|
| `"none"` | 고정 |
| `"cosine"` | 코사인 곡선으로 `LR → LR_MIN` **(기본값)** |
| `"step"` | `LR_STEP` 에폭마다 `LR_GAMMA` 배 |
| `"plateau"` | **검증 PPL 이 정체할 때만** 감소 (조기 종료와 같은 신호) |

|---|---|---|---|---|
| v0.2.1 (N=3) | 3.00 | 3.37 | 1.12배 | 209,641 |
| v0.2.2 (+초기화·정규화) | 3.24 | 3.46 | 1.07배 | 209,641 |
| **v0.2.3 (+튜닝 3종)** | 3.37 | **3.59** | 1.07배 | **207,305** |

- 임베딩을 32 → **128** 로 4배 키웠는데 파라미터는 v0.2.2 와 거의 같아요 —
  weight tying 이 `V×H`(1,225×128 ≈ **15.7만 개**)를 돌려줬거든요. **같은 예산으로 4배 넓은 표현.**

> ⚠️ **이 숫자는 실행마다 흔들려요.** 같은 설정으로 3번 돌린 결과가 **3.26 · 3.59 · 3.65** 였습니다.
> 위 3.59 는 **현재 저장된 모델**의 값이에요. 아래에서 원인을 봅니다.

## 왜 흔들리나 — `EPOCHS` 가 두 가지 일을 겸해서

`make_scheduler()` 가 cosine 의 감쇠 기간을 `T_max=self.EPOCHS` 로 잡아요. 그래서 `EPOCHS` 는

- **상한** — 최대 몇 에폭까지 돌 수 있나
- **감쇠 기간** — 학습률이 `LR → LR_MIN` 까지 내려가는 데 걸리는 에폭

**두 가지를 동시에** 뜻합니다. `EPOCHS=1500` 이면 학습률이 아주 천천히 줄어서, 한참 동안 높은 채로 머물러요.
그 구간에서는 손실이 출렁이므로 **조기 종료(patience 20)가 언제 걸리느냐가 사실상 우연**이 됩니다.

| 실행 | 멈춘 에폭 | 그때 학습률 | 검증 PPL |
|---|---|---|---|
| A | 72 | ≈ 0.0099 (거의 안 줄어듦) | 3.66 |
| B | 173 | ≈ 0.0095 | 3.59 |
| C | 1198 | ≈ 0.0003 (충분히 감쇠) | 3.26 |

- 일찍 멈추면 **감쇠가 효과를 내기 전에** 끝나요 → 나쁜 값.
- 끝까지 가면 학습률이 낮아진 구간에서 곱게 수렴해요 → 좋은 값.

> 💡 **교훈: 하이퍼파라미터 하나가 두 역할을 겸하면, 한쪽을 못 건드려요.**
> `EPOCHS` 를 늘렸더니 **오히려 덜 학습하고 끝나는** 일이 생깁니다. 상한과 스케줄 기간은
> 원래 별개 개념이니, 실전에서는 분리하는 게 맞아요 (`T_max` 를 따로 두는 식).

## 도구별 몫을 재보면 — `1.train/sweep.py`

v0.2.2 → v0.2.3 은 도구 3개와 `EMBED` 가 **함께** 바뀐 비교라, 그것만으로는 원인을 말할 수 없어요.
그래서 `E=H=128 · N=3` 을 고정한 채 **한 번에 하나만** 켜 봤습니다.

```bash
python3 1.train/sweep.py            # 5개 전부 (MPS 로 20~40분)
python3 1.train/sweep.py --runs all none
```

| 실험 | dropout | tying | schedule | 검증PPL | 파라미터 | 기준선 대비 |
|---|---|---|---|---|---|---|
| none | — | — | — | 3.5279 | 364,105 | (기준) |
| dropout | 0.1 | — | — | 3.5614 | 364,105 | +0.034 |
| tying | — | ✅ | — | 3.6355 | **207,305** | +0.108 |
| cosine | — | — | ✅ | 3.4705 | 364,105 | −0.057 |
| all | 0.1 | ✅ | ✅ | 3.6513 | **207,305** | +0.123 |

**읽는 법 — 이 표로는 도구를 구분할 수 없어요**

- 가장 큰 도구 효과가 **0.12** 인데, 같은 설정의 **실행 간 편차는 0.40** 입니다(3.26~3.66).
- **신호(0.12) < 잡음(0.40)** → 부호조차 실행마다 뒤집힐 수 있어요.
  실제로 `all` 설정의 실측치는 3.2601 · 3.5889 · 3.6513 로 제각각입니다.
- 그러니 "dropout 은 무효과", "tying 은 손해" 같은 **결론을 내리면 안 돼요.**
- 유일하게 잡음과 무관한 사실: **weight tying 은 파라미터를 43% 줄인다**(364,105 → 207,305).
  이건 측정이 아니라 구조에서 나오는 값이라 흔들리지 않아요.

> 💡 **교훈: 측정하려면 신호가 잡음보다 커야 해요.** 루트 `ablation_block_size.py` 에서 문맥 효과(±0.02)를
> 잡음으로 판정했던 것과 같은 기준이에요. 도구를 제대로 비교하려면 먼저 **편차부터 줄여야** 합니다
> (스케줄 기간을 분리하거나, 여러 시드로 평균 내거나).
