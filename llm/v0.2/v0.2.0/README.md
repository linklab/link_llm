# link_llm — 나만의 작은 언어 모델 (v0.2.0)

**임베딩 도입 (one-hot → `nn.Embedding`).** 신경망 시대 2막의 시작이에요.
토큰을 '독립된 칸(one-hot)'이 아니라 **작은 연속 벡터(임베딩)** 로 표현합니다.

## v0.1.5 → v0.2.0, 무엇이 바뀌었나요?

> **딱 '입력 표현' 하나.** 앞 2토큰 문맥·2층 MLP·정규화·저장방식은 v0.1.5 그대로,
> 입력만 one-hot(2V) → **임베딩 concat(2E)** 로 바꿔요.

| | v0.1.5 (one-hot) | v0.2.0 (임베딩) |
|---|---|---|
| 토큰 표현 | one-hot (V차원, 독립) | 임베딩 (E차원, 공유·학습) |
| 입력 크기 | 2V (예: 1586) | **2E (예: 64)** |
| 모델 | `Linear(2V,H)→tanh→Linear(H,V)` | `Embedding(V,E)` + `Linear(2E,H)→tanh→Linear(H,V)` |
| 새 표 | — | 임베딩 표 `C` (V×E, 함께 학습) |

## 핵심 통찰 — 임베딩 = one-hot 곱하기의 압축판

```python
nn.Embedding(V, E)(idx)  ==  F.one_hot(idx, V).float() @ C     # C: V×E
```

'원-핫 곱하기 가중치'가 곧 '표에서 한 줄 꺼내기(lookup)'예요. one-hot 의 첫 층을
임베딩 lookup 으로 바꾼 것 — 결과 형태는 같지만 **E ≪ V 로 압축·공유**된다는 게 핵심이에요.

## 왜 임베딩이 중요한가

- **one-hot 의 한계**: 토큰마다 독립된 칸 → "안녕 다음"에서 배운 걸 "반가워 다음"에 못 씀.
- **임베딩**: 비슷한 토큰이 비슷한 벡터를 갖도록 학습 → **문맥끼리 강점을 공유** →
  처음 보는 조합도 부드럽게 일반화 → 카운트의 백오프를 이길 진짜 무기.

## 구조 (Bengio 2003)

```
(앞앞, 앞) → 임베딩 lookup(각 E) → concat(2E) → fc1 → tanh → fc2 → logits(V)
```

```bash
python3 3.train/train.py     # 임베딩 MLP 학습 → 2.models/model.pt (+ vocab.json)
python3 4.test/test.py       # 학습/검증 PPL + 대화 예시
```

검증 PPL 이 **v0.1.5(one-hot 2토큰) 보다 내려가면** "임베딩의 공유 표현이 일반화에 도움",
더 내려가 **v0.0.9(카운트) 34.39** 아래면 드디어 신경망이 카운트를 넘어선 거예요.

## 측정된 결과 (기본 하이퍼파라미터)

| 모델 | 학습 PPL | 검증 PPL | top-1 정확도 | 후보有 |
|---|---|---|---|---|
| v0.0.9 카운트 (앞 2토큰 + 백오프) | 2.79 | 34.39 | 45.5% | 72.0% |
| v0.1.5 one-hot 2토큰 신경망 | 3.60 | **31.81** | **47.1%** | 83.6% |
| **v0.2.0 임베딩 2토큰 신경망** | 3.74 | 32.76 | 46.6% | 83.6% |

- 카운트 기준선(34.39)은 **넘었어요** ✅
- 하지만 **one-hot(v0.1.5)은 아직 못 이겨요** — PPL 도 정확도도 근소하게 뒤집니다.
  학습 문장이 282개뿐이라, "비슷한 토큰끼리 벡터를 공유해 아낀다"는 임베딩의 장점보다
  토큰마다 독립된 칸을 갖는 one-hot 의 **구별력**이 아직 더 크거든요.
- 대신 **파라미터는 12% 적고**(538,650 vs 610,842) **더 적은 에폭에 도달**해요
  (조기 종료 기준 44 vs 106 에폭). 임베딩이 사주는 건 아직 '정확도'가 아니라 '효율'입니다.

이건 `EMBED`(E) 를 키워 보면 바로 드러나요 — E 가 클수록(= one-hot 에 가까워질수록) 좋아집니다:

| EMBED(E) | 32 | 64 | 128 | **256** | 512 |
|---|---|---|---|---|---|
| 검증 PPL (5시드 평균) | 37.6 | 36.9 | 35.3 | **32.9** | 34.5 |

> **결론:** 임베딩의 '압축이 이득'이 되려면 **데이터가 더 필요해요.** 이 데이터 규모에서
> 임베딩이 주는 건 "one-hot 과 비슷한 성능을 **더 적은 에폭**(50 vs 100)에" 정도예요.
> 진짜 이득은 문맥이 길어지고(v0.2.1) 데이터가 늘어날 때 나타납니다 —
> one-hot 은 문맥 N토큰에 입력이 `N×V` 로 폭발하지만 임베딩은 `N×E` 로만 늘거든요.

## 하이퍼파라미터를 어떻게 골랐나

`3.train/train.py` 의 기본값은 **에폭별 검증 PPL 곡선 × 8개 시드**를 재서 고른 값이에요.
직접 바꿔볼 때 참고할 실측 정리:

- **`LR` 이 가장 중요해요.** Adam 은 `1e-4 ~ 1e-3` 대가 정상입니다.
  (`LR=0.05` 로 두면 검증 PPL 이 **144** 까지 치솟아요 — 학습이 수렴하지 않고 튕겨 다녀요.)
- **`EPOCHS` 는 작게.** 학습 짝이 2,180개뿐이라 50 에폭 근처가 바닥이고, 그 뒤로는
  과적합으로 검증 PPL 이 계속 올라가요 (100→36, 200→39).
- **`WEIGHT_DECAY` 는 0.** 1e-4 만 켜도 검증 PPL 이 나빠져요.
- **`LABEL_SMOOTHING` 도 0.** `perplexity()` 가 이미 `FLOOR`(1e-4)로 최소 확률을 깔아주기 때문에
  (= 카운트의 add-k 스무딩과 같은 역할) 라벨 스무딩은 중복이고, 정답 확률만 깎아요.
- **시드 편차가 커요** (같은 설정에서 ±1.2). 한 번 돌린 숫자로 결론 내지 말고 `SEED` 를
  바꿔 두세 번 재보세요.

## 저장 형식 (v0.1.x 와 동일 방식)

- `model.pt` : `torch.save(net.state_dict())` — 임베딩 표 `emb.weight`(V×E)도 함께 저장.
- `vocab.json` : `{ tokenizer, vocab }`.
- 불러올 때 `emb.weight` 모양에서 **임베딩 차원 E**, `fc1.weight` 에서 **은닉 H** 를 복원.
