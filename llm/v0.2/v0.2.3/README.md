# link_llm — 나만의 작은 언어 모델 (v0.2.3)

**일반화 · 튜닝.** 모델 구조·문맥은 v0.2.2 그대로이고, **학습을 다듬는 도구 3개**를 더합니다.

## 한 걸음 — 도구 3개

| # | 도구 | 코드 | 무엇을 하나 |
|---|---|---|---|
| ① | **dropout** | `nn.Dropout(p)` (tanh 뒤) | 학습 중 은닉 뉴런 일부를 꺼 특정 경로 의존을 막음 |
| ② | **weight tying** | `fc2.weight = emb.weight` | 출력층과 임베딩이 **한 텐서를 공유** → 파라미터 V×H 절약 |
| ③ | **LR 스케줄** | `torch.optim.lr_scheduler` | 학습이 진행될수록 학습률을 줄여 곱게 수렴 |

## 구조

```
(앞 N토큰) → 임베딩 concat(N·E) → fc1 → [BatchNorm(선택)] → tanh → [Dropout] → fc2 → logits(V)
                                                                                ↑ (선택) emb.weight 공유
```

- `DROPOUT=0.0` 이면 Dropout 이 항등이라 **v0.2.2 와 완전히 같아져요**.
- **weight tying 은 `HIDDEN == EMBED` 가 필수**입니다 (`fc2.weight`(V,H) 와 `emb.weight`(V,E) 모양이 같아야 함).
  어긋나면 `lm.py` 가 이유를 설명하며 멈춰요.

| `LR_SCHEDULE` | 동작 |
|---|---|
| `"none"` | 고정 |
| `"cosine"` | 코사인 곡선으로 `LR → LR_MIN` **(기본값)** |
| `"step"` | `LR_STEP` 에폭마다 `LR_GAMMA` 배 |
| `"plateau"` | **검증 PPL 이 정체할 때만** 감소 (조기 종료와 같은 신호) |

> 쉬운 데이터에선 정규화·튜닝이 값을 못 합니다. 아래에서 `EPOCHS` 문제도 함께 봅니다.

## `EPOCHS` 가 두 가지 일을 겸해요 (구조상 주의점)

`make_scheduler()` 가 cosine 의 감쇠 기간을 `T_max=self.EPOCHS` 로 잡아요. 그래서 `EPOCHS` 는

- **상한** — 최대 몇 에폭까지 돌 수 있나
- **감쇠 기간** — 학습률이 `LR → LR_MIN` 까지 내려가는 데 걸리는 에폭

**두 가지를 동시에** 뜻합니다. `EPOCHS` 를 크게 잡으면 감쇠가 예산 안에서 못 끝나고,
조기 종료가 걸릴 때까지도 학습률이 덜 줄어 있어요.

| 버전 | `EPOCHS` | 멈춘 에폭 | 검증 PPL |
|---|---|---|---|
| v0.2.3 | 1,500 | 232 | 2.65 |
| **v0.2.5** | **300** | 246 | **2.64** |

- 지금 설정(`LR=0.0003`)에선 차이가 **0.01** 로 작아요 — 학습률이 처음부터 낮아 덜 민감합니다.
- 그래도 **상한과 스케줄 기간은 원래 별개 개념**이에요. 하나가 두 역할을 겸하면
  `EPOCHS` 를 늘리는 것만으로 학습률 곡선이 통째로 바뀌어, 한쪽을 못 건드리게 됩니다.
- 실전 해법은 `T_max` 를 `EPOCHS` 에서 **분리**하는 것이고, v0.2.5 는 코드를 안 바꾸는 선에서
  **감쇠가 예산 안에서 끝나는 값을 고르는 것**으로 대신했어요.

> 💡 **교훈: 하이퍼파라미터 하나가 두 역할을 겸하면, 한쪽을 못 건드려요.**

## 도구별 몫을 재보면 — `1.train/sweep.py`

v0.2.2 → v0.2.3 은 도구 3개가 **함께** 켜진 비교라, 그것만으로는 원인을 말할 수 없어요.
그래서 `E=H=256 · N=3` 을 고정한 채 **한 번에 하나만** 켜 봤습니다.

```bash
python3 1.train/sweep.py            # 5개 전부 (MPS 로 30~60분)
python3 1.train/sweep.py --runs all none
```

| 실험 | dropout | tying | schedule | 검증PPL | 파라미터 | 기준선 대비 |
|---|---|---|---|---|---|---|
| none | — | — | — | 2.6475 | 661,129 | (기준) |
| dropout | 0.1 | — | — | 2.6446 | 661,129 | −0.003 |
| tying | — | ✅ | — | 2.6493 | **429,449** | +0.002 |
| cosine | — | — | ✅ | 2.6470 | 661,129 | −0.001 |
| all | 0.1 | ✅ | ✅ | 2.6453 | **429,449** | −0.002 |

**읽는 법 — 세 도구 다 PPL 에는 영향이 없어요**

- 다섯 설정이 전부 **2.644 ~ 2.649** 안에 들어옵니다. 최대 차이가 **0.003**,
  소수점 둘째 자리에서는 아예 구분이 안 돼요.
- v0.1.3(정규화)·v0.2.2(초기화) 와 **같은 결론**이에요 — 쉽고 작은 데이터에 조기 종료까지
  걸려 있으면, 과적합을 막는 도구는 더 얹을 게 없습니다.
- ✅ **다만 weight tying 은 값을 해요 — PPL 이 아니라 크기에서.**
  PPL 은 +0.002(사실상 동일)인데 파라미터는 **661,129 → 429,449 (−35%)**.
  **공짜로 3분의 1을 덜어내는 셈**이에요.

> 💡 **교훈: 도구의 값어치는 지표 하나로 재지 마세요.** PPL 만 봤다면 tying 은 "미세하게 손해"로
> 읽혔을 텐데, 크기를 함께 보면 **이 표에서 유일하게 값을 하는 도구**입니다.
